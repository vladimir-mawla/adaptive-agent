# ADR 0008 — M8 the interactive demo: a pure replay-fold view-model, why the engine can never be handed a throwing input, the spelling-drift disclosure, and the deploy exception

- **Date:** 2026-09-30
- **Status:** accepted
- **Phase / milestone:** M8 (BUILD) — `app/page.tsx`, `components/AdaptiveAgentDemo.tsx`,
  `components/compute-demo-view.ts`, `components/__tests__/*.test.ts(x)`

## Context

`.genesis/PLAN.md` §3 (M8) commits this milestone to "live knob panels: inject episodes and watch
`hold -> adopt -> revert` fire, versus the invariant knob that never moves" — a person must be able
to change something (inject an `Episode`, choosing its `contextId`/`outcome`/target knob) and watch
a real `AdaptationDecision` update, rendered from a real `tally` -> `gate` -> `arbitrate` call, never
a hardcoded string describing what the engine "would" do. `lib/**`, `domains/**`, and
`tests/failures/**` are all FROZEN for this milestone. This ADR records the view-model design, a
real bug this milestone's own build found and fixed (not merely a design choice stated in advance),
the two structural throw-conditions `lib/arbitrate.arbitrate` carries and why this UI cannot
construct either, the spelling-drift decision, and the deploy exception this round operates under.

## Decision 1 — one pure, synchronous replay-fold function, no `useEffect`/`useCallback`/`async` anywhere

`components/compute-demo-view.ts`'s `computeKnobView(knobId, inputs)` takes the FULL ordered history
of what a person has injected against one knob and replays it, from scratch, on every call: each
`RawEpisodeInput` becomes a real `Episode` (via `lib/contracts`' own branding functions), and each
one is evaluated through `domains/support-triage/scenario.ts`'s own `evaluateDelta` (the identical
`tally` -> `gate` -> `arbitrate` glue `scripts/demo-triage.ts` already uses) — never a second,
independently-written copy of that composition.

This is a pure function of its own arguments: the same `inputs` array always produces the same
`KnobView`, proven by `components/__tests__/compute-demo-view.test.ts`'s own "purity" test (`toEqual`
across two separate calls with the identical input). `AdaptiveAgentDemo.tsx` calls it fresh on every
render, straight from `useState`-held input history — no ref, no memo, no effect caches a phase or a
decision separately from what a render just computed. `lib/**` is entirely synchronous, so there is
no asynchronous boundary this component's own state could ever race against; deriving everything
during render is simplest and provably free of the "stale derived state" trap a sibling project's own
M8 build flagged.

## Decision 2 — the two-phase replay-fold model, and a real bug this milestone's own build found

`lib/arbitrate.arbitrate` takes exactly one `tally` and one `priorState` per call and has no memory
of a delta's own evidence history — `scenario.ts`'s own header already names this gap and records its
fix: each phase (pre-adoption trial, post-adoption monitoring) gets its own fresh episode pool. This
file makes the identical choice, for the identical reason, replaying injected episodes against a
phase that starts `"trial"` (`priorState: vacant`) and flips to `"live"` (`priorState: live`, rolling
back to `delta.from`) the instant a trial-phase evaluation first resolves `adopt`.

**The bug, found by writing the falsifiable test for it, not guessed at in advance:** the first
working draft of `computeKnobView` folded the phase transition correctly but then threw away the
decision that CAUSED it — after the loop, it re-evaluated once more, against whichever pool the
FINAL phase pointed at. For a delta that adopts on its very last injected episode (the common case:
inject exactly 3 distinct helped episodes, nothing more), this meant re-evaluating against an
as-yet-EMPTY `monitoring` pool under `live` — which still happens to resolve `kind: "adopt"` (an
empty tally cannot clear the revert bar either), so the test `expect(view.decision.kind).toBe(
"adopt")` passed, while `expect(view.decision.tally.distinctContexts).toBe(3)` failed: the displayed
`AdaptationDecision` claimed a real adoption while citing zero evidence for it, silently. This was
caught by `npm test` on the very first run of the test file that exercises it (see this milestone's
PR report for the raw failure), not discovered later.

**The fix:** track `decision` incrementally, inside the fold itself — after each episode is pushed to
whichever pool is currently active, re-evaluate immediately and keep THAT decision as `computeKnobView`'s
own return value; never a separate final re-evaluation after the loop. `scripts/demo-triage.ts` avoids
this same trap by construction (it prints a fresh decision after every individual episode is added,
never once at the end); this file now follows the identical discipline, and the "purity/construction
invariants" describe *why* re-deriving the whole thing per render is still safe even though the fold
is stateful internally — the WHOLE fold re-runs from `inputs` every call, so there is nothing to go
stale.

## Decision 3 — why this UI structurally cannot hand `arbitrate` an input that throws

`lib/arbitrate/arbitrate.ts` throws on exactly two conditions (read directly off its source, not
inferred): `tally.deltaId !== delta.id`, and `gateResult === "frozen"` with no invariant in the
supplied registry naming `delta.knob` (an inconsistent `gateResult`/`registry` pair). A third
condition sometimes assumed to exist — duplicate ids — was checked directly against
`lib/arbitrate/arbitrate.ts`'s full source (`grep -n "throw new Error"`) and does not exist anywhere
in the frozen engine; this file's own header (Decision 3 here) states that plainly rather than
building a defensive check against a failure mode that isn't real.

This file never builds a `tally` or a `gateResult` by hand — it calls `evaluateDelta`
(`scenario.ts`, FROZEN), which always tallies with `delta.id` itself (`tally(delta.id,
episodesForThisPhase)`) and always gates against this domain's one `SUPPORT_TRIAGE_REGISTRY`. So the
pair `arbitrate` receives is consistent BY CONSTRUCTION — there is no code path in this file or in
`AdaptiveAgentDemo.tsx` that assembles either value independently of that one call. The three
`BehaviorDelta` values (`DEMO_DELTAS`) are fixed module-level constants with distinct, hardcoded ids
(`demo-delta-escalation-aggressiveness`, `demo-delta-response-directness`,
`demo-delta-auto-refund-ceiling`) — nothing in the rendered form lets a person type or choose a delta
id at all, only a `contextId` and an `outcome` for a knob they pick from a closed three-option
`<select>`. `components/__tests__/compute-demo-view.test.ts`'s "construction invariants" tests pin
this: the three ids are distinct, and each delta's own `knob` field matches the key it is registered
under.

**Consequence, stated at its true strength:** this is a claim about THIS UI's own construction, not a
proof that no `BehaviorDelta`/`EvidenceTally` pair could ever throw `arbitrate` — a caller willing to
build one by hand still can (that is exactly what `tests/failures/10-revert-trusts-caller-supplied-
prior-value.test.ts` and the M5 unit suite already exercise). This file's contribution is narrower and
concrete: no sequence of clicks a person can perform against the rendered form reaches either throw
condition.

## Decision 4 — the spelling-drift limit is surfaced honestly, not normalized away

M7's own case 6 (`tests/failures/06-context-id-spelling-drift.test.ts`) pins that `"tck-1"`,
`"TCK-1"`, and `" tck-1 "` count as three distinct contexts — `lib/evidence/tally.ts` dedups by exact
string equality, with no normalization anywhere in this codebase (a deliberate, disclosed non-goal,
the same "no parsing machinery" discipline this account's own standing instruction names). Since this
UI lets a person type a free-text `contextId`, they CAN hit this — and this milestone's own "traps"
section requires a decision, not a default.

**The decision:** surface it honestly, the way M6's own demo does at step 7, rather than avoid it.
`AdaptiveAgentDemo.tsx`'s injection form carries a permanent, visible note next to the context-id
field naming the exact three-way example from M6/M7 and stating plainly that this demo does not
normalize input. No trimming, case-folding, or Unicode normalization is applied anywhere in
`compute-demo-view.ts` before a typed string reaches `contextId()` — the raw string a person typed is
exactly what becomes the `Episode`'s own `contextId`.

**Why surfacing it beats avoiding it, for this specific artifact:** this demo's entire reason to
exist is showing a person how corroboration accumulates from real, distinct occasions — hiding the
one honestly-disclosed case where "distinct" and "the same ticket" diverge would misrepresent the
engine's actual behavior inside the one artifact whose whole job is representing that behavior
faithfully. `components/__tests__/compute-demo-view.test.ts` pins both directions: the same ticket
typed three ways clears `MIN_DISTINCT_CONTEXTS_ADOPT` (3), while the identical ticket typed the exact
same way three times stays at `distinctContexts: 1` and holds.

## Decision 5 — one shared injection form with a knob selector, not three independent forms

The plan's own "at minimum" bullet asks for: add episodes with a chosen outcome and context id, pick
which knob a delta targets, and watch the tally/gate verdict/decision update. A single form (context
id, outcome, and a `<select>` naming all three `DEMO_KNOB_IDS`) satisfies "pick which knob a delta
targets" directly and keeps the interactive surface small — one path for injection, not three
near-identical ones to keep in sync. Each of the three panels below it is a pure read of
`computeKnobView` for that knob; none of them carries their own, second copy of the injection UI.

## Decision 6 — revert is not "sticky" across further evidence, disclosed rather than silently assumed

`lib/arbitrate.arbitrate` is fully stateless: given the identical `priorState: live` and a fresh
`EvidenceTally`, it re-derives `revert` vs. `adopt` from that tally alone, with no memory of a PRIOR
call's own `revert` ruling. This file's own fold reflects that honestly: once a knob's phase reaches
`"live"`, every subsequently injected episode is added to a single, growing `monitoringEpisodes` pool
and re-evaluated against the WHOLE pool each time — so if a person injects enough further `"helped"`
episodes after a `revert` to flip `harmedMajority` back to false, the displayed decision will flip
back to `adopt`. This is not a bug this file introduces; it is what `arbitrate`'s own documented
contract produces when a caller (this UI) does not separately track "this delta was rolled back and
should never be reconsidered." Building that tracking was considered and left out: `lib/arbitrate`'s
own module comment already states plainly that tracking a knob's live/reverted history "is the
CALLER's job, not this function's," and inventing a persisted "permanently retired" flag this
milestone's own scope does not ask for would be exactly the kind of speculative flexibility this
account's own standing discipline warns against paying for in unplanned rounds. Recorded here as a
disclosed consequence, not silently hidden behind a UI that stops accepting input once `revert`
fires.

## Decision 7 — `docs/WALKTHROUGH.md` was written now, against `localhost:3000`, not the deployed URL

`.genesis/PLAN.md` §3 (M8)'s own falsifiable check requires "a WALKTHROUGH.md script, beat-by-beat,
verified against the deployed URL in the same session it's written." Two tensions with that literal
text, both resolved here rather than silently either skipped or worked around:

1. **`docs/WALKTHROUGH.md` is nominally `M9`'s own file** — plan §3 (M9)'s "Scope" list names it
   directly, and M8's own "Files it owns" bullet does not. This is a real plan-boundary gap: M8's OWN
   falsifiable check cannot be satisfied without producing a file M9 is also named as owning. This
   milestone resolves it by writing the file now, since M8's falsifiable check is concrete and
   present-tense ("verified... in the same session it's written") while M9 has not started — M9
   should treat this file as already delivered and revise it if a later milestone's own scope
   requires changes, not re-invent it from scratch.
2. **Deploying was explicitly out of scope for this round** (see this milestone's own PR/report): the
   Vercel CLI was logged out and `VERCEL_TOKEN` was not in the environment, with the token mid-
   rotation by the account holder. "Verified against the deployed URL" was substituted with
   "verified against a real, running `npm run dev` session on this machine" — every beat in
   `docs/WALKTHROUGH.md`'s own verification section was captured from an actual browser session
   against `localhost:3000` in this same session, not written from intentions and checked later. This
   substitution is stated plainly at the top of that file and is not silently narrowed into the
   original plan language.

**No forward promise is made about when the deployed URL will reflect this milestone** — only that it
currently does not, and that `docs/WALKTHROUGH.md` names this explicitly.

## Falsifiability — the gutting experiment, run for real

`computeKnobView`'s entire replay-fold body was temporarily replaced with a stub that ignores its own
`inputs` parameter (every knob permanently evaluated against zero episodes, forever `"trial"` phase),
kept typecheck-clean (`void inputs; void toEpisode; void liveOn;`) so the count below reflects semantic
sensitivity, not an unrelated build break. `npm test` was then run against the full suite:

- **353 of 360 tests still passed; 7 failed**, all seven inside
  `components/__tests__/compute-demo-view.test.ts`:
  - `2 distinct helped episodes -> still TRIAL, hold, needs 1 more`
  - `3 distinct helped episodes -> flips to LIVE, adopt`
  - `one post-adoption harmed episode is NOT enough to revert (asymmetric bar, but not zero)`
  - `a SECOND distinct post-adoption harmed episode flips it to revert, rolling back to delta.from`
  - `FALSIFIABILITY: a same-context replay storm never reaches adopt — 50 repeats of one ticket is still distinctContexts: 1`
  - `the same ticket typed three ways (case + whitespace) counts as three distinct contexts and clears adopt`
  - `the identical ticket typed the SAME way three times stays exactly one context and holds`
- **Decomposed, the 9 tests in that same file that did NOT fail are not a gap in coverage — each is
  correctly insensitive to this specific sabotage, for a stated reason:**
  - `zero episodes -> TRIAL phase, hold, needs 3 more distinct contexts` — the gutted function's own
    fixed output IS the correct zero-episode answer.
  - The four `auto-refund-ceiling` tests (zero episodes; 5 overwhelming episodes; 10,000-episode
    flood; "never leaves trial") — correctly pass under this sabotage, because `frozen` is SUPPOSED
    to be identical regardless of episode count; a sabotage that makes evidence irrelevant cannot, by
    definition, break a property that says evidence must already be irrelevant here. This is the
    gutting experiment confirming, not weakening, that specific claim.
  - The "purity" test — still passes, because a function that ignores its input is still
    deterministic (pure), just wrong; purity and correctness are different properties and this test
    only claims the former.
  - The two "construction invariant" tests (distinct ids; `knob` field matches its key) — assert
    facts about `DEMO_DELTAS` itself, never about `computeKnobView`'s own replay logic.
  - `components/__tests__/AdaptiveAgentDemo.test.tsx`'s render-smoke tests also passed unchanged
    under this sabotage — a disclosed, correctly-scoped limit of a STATIC-markup smoke test: it
    renders the zero-episode initial state only and cannot simulate a click, so it was never going to
    catch a bug that only manifests after interaction. This is exactly why `docs/WALKTHROUGH.md` and
    this milestone's own PR report also record a REAL, driven browser session — the render-smoke test
    proves the component renders; it does not and cannot prove the interaction works.
- `components/compute-demo-view.ts` was then restored byte-for-byte (`diff` against the pre-sabotage
  copy confirmed identical), `npm run typecheck` and `npm test` re-run clean (360/360), before any
  commit was made.

## What this milestone does not claim

- **Not a claim that `arbitrate` can never throw for any caller** — only that this UI's own
  construction cannot reach either of its two real throw conditions (Decision 3).
- **Not a claim that revert is permanent** — Decision 6 discloses the opposite: further evidence can,
  in principle, flip a reverted knob back to `adopt`, matching `arbitrate`'s own stateless contract.
- **Not a claim that the deployed URL reflects this milestone** — Decision 7 and this milestone's own
  PR/report both state plainly that it does not yet.
- **Not a claim about M9.** This ADR records that `docs/WALKTHROUGH.md` was written now because M8's
  own falsifiable check required it; it makes no promise about what M9 will or will not do with it,
  and no claim that any other M9-scoped document (README's "Limits" section, `docs/ARCHITECTURE.md`,
  `docs/THESIS.md`, `docs/NOTES.md`, the Loom recording itself) exists yet.
