# ADR 0008 — M8 the interactive demo: a pure replay-fold view-model, why the engine can never be handed a throwing input, the spelling-drift disclosure, and the deploy exception

- **Date:** 2026-09-30
- **Status:** accepted
- **Phase / milestone:** M8 (BUILD) — `app/page.tsx`, `components/AdaptiveAgentDemo.tsx`,
  `components/compute-demo-view.ts`, `components/__tests__/*.test.ts(x)`

## Context

`.genesis/PLAN.md` §3 (M8) commits this milestone to "live knob panels: inject episodes and watch
`hold -> adopt -> revert` fire, versus the invariant knob that never moves" — a person must be able
to change something (inject an `Episode`, choosing its `contextId`/`outcome`/target knob) and watch
a real `AdaptationDecision` update, rendered from a real `tally` -> `gate` -> `arbitrate` call, never
a hardcoded string describing what the engine "would" do. `lib/**`, `domains/**`, and
`tests/failures/**` are all FROZEN for this milestone. This ADR records the view-model design, a
real bug this milestone's own build found and fixed (not merely a design choice stated in advance),
the throw sites in `lib/arbitrate.arbitrate` (three, of which two are caller-inducible), why this UI
reaches none of them, and the one throw site this milestone itself adds, the spelling-drift decision,
and the deploy exception this round operates under.

## Decision 1 — one pure, synchronous replay-fold function, no `useEffect`/`useCallback`/`async` anywhere

`components/compute-demo-view.ts`'s `computeKnobView(knobId, inputs)` takes the FULL ordered history
of what a person has injected against one knob and replays it, from scratch, on every call: each
`RawEpisodeInput` becomes a real `Episode` (via `lib/contracts`' own branding functions), and each
one is evaluated through `domains/support-triage/scenario.ts`'s own `evaluateDelta` (the identical
`tally` -> `gate` -> `arbitrate` glue `scripts/demo-triage.ts` already uses) — never a second,
independently-written copy of that composition.

This is a pure function of its own arguments: the same `inputs` array always produces the same
`KnobView`, proven by `components/__tests__/compute-demo-view.test.ts`'s own "purity" test (`toEqual`
across two separate calls with the identical input). `AdaptiveAgentDemo.tsx` calls it fresh on every
render, straight from `useState`-held input history — no ref, no memo, no effect caches a phase or a
decision separately from what a render just computed. `lib/**` is entirely synchronous, so there is
no asynchronous boundary this component's own state could ever race against; deriving everything
during render is simplest and provably free of the "stale derived state" trap a sibling project's own
M8 build flagged.

## Decision 2 — the two-phase replay-fold model, and a real bug this milestone's own build found

`lib/arbitrate.arbitrate` takes exactly one `tally` and one `priorState` per call and has no memory
of a delta's own evidence history — `scenario.ts`'s own header already names this gap and records its
fix: each phase (pre-adoption trial, post-adoption monitoring) gets its own fresh episode pool. This
file makes the identical choice, for the identical reason, replaying injected episodes against a
phase that starts `"trial"` (`priorState: vacant`) and flips to `"live"` (`priorState: live`, rolling
back to `delta.from`) the instant a trial-phase evaluation first resolves `adopt`.

**The bug, found by writing the falsifiable test for it, not guessed at in advance:** the first
working draft of `computeKnobView` folded the phase transition correctly but then threw away the
decision that CAUSED it — after the loop, it re-evaluated once more, against whichever pool the
FINAL phase pointed at. For a delta that adopts on its very last injected episode (the common case:
inject exactly 3 distinct helped episodes, nothing more), this meant re-evaluating against an
as-yet-EMPTY `monitoring` pool under `live` — which still happens to resolve `kind: "adopt"` (an
empty tally cannot clear the revert bar either), so the test `expect(view.decision.kind).toBe(
"adopt")` passed, while `expect(view.decision.tally.distinctContexts).toBe(3)` failed: the displayed
`AdaptationDecision` claimed a real adoption while citing zero evidence for it, silently. This was
caught by `npm test` on the very first run of the test file that exercises it (see this milestone's
PR report for the raw failure), not discovered later.

**The fix:** track `decision` incrementally, inside the fold itself — after each episode is pushed to
whichever pool is currently active, re-evaluate immediately and keep THAT decision as `computeKnobView`'s
own return value; never a separate final re-evaluation after the loop. `scripts/demo-triage.ts` avoids
this same trap by construction (it prints a fresh decision after every individual episode is added,
never once at the end); this file now follows the identical discipline, and the "purity/construction
invariants" describe *why* re-deriving the whole thing per render is still safe even though the fold
is stateful internally — the WHOLE fold re-runs from `inputs` every call, so there is nothing to go
stale.

## Decision 3 — why this UI structurally cannot hand `arbitrate` an input that throws

`lib/arbitrate/arbitrate.ts` contains three `throw new Error` sites (lines 174, 245 and 255 at this
commit; `grep -n "throw new Error" lib/arbitrate/arbitrate.ts` returns exactly those three). Two are
caller-inducible: `tally.deltaId !== delta.id`, and `gateResult === "frozen"` with no invariant on
`delta.knob` in the supplied registry. The third (`buildFrozenDecision`) is a defence-in-depth guard
on a literal the function has just built; `assertFrozenCitesNoEvidence` cannot fail on it, so no
caller input reaches it. This UI reaches none of the three.

A condition the brief for this milestone listed alongside these, "duplicate ids", is not one of the
three: no duplicate-id check exists in `lib/arbitrate`, nor anywhere else in the frozen engine (the
only other `throw new Error` in non-test `lib/**` is `assertNeverAdaptationDecision`, an exhaustiveness
helper that `describeDecision`'s unreachable `default` branch calls). This ADR records that rather than
building a defensive check against a failure mode that is not real. (An earlier revision of this
paragraph said `arbitrate` throws on "exactly two conditions" and cited that same `grep` as proof; the
`grep` returns three, so "two" is defensible only as "caller-inducible". L4 VERIFY caught the
mismatch.)

**A fourth throw site exists, and it is this milestone's own:** `mustEvaluate` in
`components/compute-demo-view.ts` throws if `evaluateDelta` reports that `lib/evidence.tally` refused
an episode set. That is reachable only if `tally` refuses (a hostile getter or `Proxy`, a non-string
field, an outcome outside the closed set, a mismatched `deltaId`) — none of which the rendered controls
can cause: the outcome comes from a closed three-option `<select>`, the context id is always a string
whatever is typed, and every episode is built inside `computeKnobView` with the knob's own delta id.
It is deliberately not caught: a view-model that silently fabricated a decision after the engine
refused would be the failure M8 exists to avoid.

This file never builds a `tally` or a `gateResult` by hand — it calls `evaluateDelta`
(`scenario.ts`, FROZEN), which always tallies with `delta.id` itself (`tally(delta.id,
episodesForThisPhase)`) and always gates against this domain's one `SUPPORT_TRIAGE_REGISTRY`. So the
pair `arbitrate` receives is consistent BY CONSTRUCTION — there is no code path in this file or in
`AdaptiveAgentDemo.tsx` that assembles either value independently of that one call. The three
`BehaviorDelta` values (`DEMO_DELTAS`) are fixed module-level constants with distinct, hardcoded ids
(`demo-delta-escalation-aggressiveness`, `demo-delta-response-directness`,
`demo-delta-auto-refund-ceiling`) — nothing in the rendered form lets a person type or choose a delta
id at all, only a `contextId` and an `outcome` for a knob they pick from a closed three-option
`<select>`.

**What is and is not pinned by a test, stated narrowly.** The two "construction invariant" tests pin
only the constants themselves: the three ids are distinct, and each delta's `knob` field matches the
key it is registered under. A mutant giving two knobs the same id fails that one test and
nothing else, correctly — each knob's episodes are built from its own delta and evaluated
independently, so a shared id does not by itself reach `arbitrate`. What pins "the pair `arbitrate`
receives is consistent" is: (a) this file never bypassing `evaluateDelta`, which is a property of the
source, not of any test; (b) the sweep test, which asserts for all three knobs at every prefix of one
fixed mixed 9-episode history that every episode the VIEW RETAINS carries that knob's own delta id and
that the displayed tally's `deltaId` matches, together with the engine-spy test, which asserts that
the episodes `evaluateDelta` is called with carry the protected knob's delta id and that `arbitrate`'s
tally carries it too (Round 3); and (c) `arbitrate`'s own throw, which would fail the
view-model tests loudly if the property were ever violated.

**Consequence, stated at its true strength:** this is a claim about THIS UI's own construction, not a
proof that no `BehaviorDelta`/`EvidenceTally` pair could ever throw `arbitrate` — a caller willing to
build one by hand still can (that is exactly what `tests/failures/10-revert-trusts-caller-supplied-
prior-value.test.ts` and the M5 unit suite already exercise). This file's contribution is narrower and
concrete: no sequence of clicks a person can perform against the rendered form reaches any of the
three throw sites in `arbitrate`, or the fourth in `mustEvaluate`. An independent verifier fuzzed
4,000 random `computeKnobView` calls (including `__proto__`, NUL, right-to-left overrides and a
1,000,000-character string) with zero throws; this repo's own suite carries a fixed adversarial corpus
of the same shape (`a fixed corpus of adversarial strings does not make the view-model throw`, which
includes a 1,048,576-character string), a regression pin and not a proof.

## Decision 4 — the spelling-drift limit is surfaced honestly, not normalized away

M7's own case 6 (`tests/failures/06-context-id-spelling-drift.test.ts`) pins that `"tck-1"`,
`"TCK-1"`, and `" tck-1 "` count as three distinct contexts — `lib/evidence/tally.ts` dedups by exact
string equality, with no normalization anywhere in this codebase (a deliberate, disclosed non-goal,
the same "no parsing machinery" discipline this account's own standing instruction names). Since this
UI lets a person type a free-text `contextId`, they CAN hit this — and leaving it undecided would
still be a decision, made by omission: the page would silently count three spellings as three
contexts with nothing on it saying so.

**The decision:** surface it honestly, the way M6's own demo does at step 7, rather than avoid it.
`AdaptiveAgentDemo.tsx`'s injection form carries a permanent, visible note next to the context-id
field naming the exact three-way example from M6/M7 and stating plainly that this demo does not
normalize input. No trimming, case-folding, or Unicode normalization is applied anywhere in
`compute-demo-view.ts` before a typed string reaches `contextId()` — the raw string a person typed is
exactly what becomes the `Episode`'s own `contextId`.

**Why surfacing it beats avoiding it, for this specific artifact:** this demo's entire reason to
exist is showing a person how corroboration accumulates from real, distinct occasions — hiding the
one honestly-disclosed case where "distinct" and "the same ticket" diverge would misrepresent the
engine's actual behavior inside the one artifact whose whole job is representing that behavior
faithfully. `components/__tests__/compute-demo-view.test.ts` pins both directions: the same ticket
typed three ways clears `MIN_DISTINCT_CONTEXTS_ADOPT` (3), while the identical ticket typed the exact
same way three times stays at `distinctContexts: 1` and holds.

## Decision 5 — one shared injection form with a knob selector, not three independent forms

The plan's own "at minimum" bullet asks for: add episodes with a chosen outcome and context id, pick
which knob a delta targets, and watch the tally/gate verdict/decision update. A single form (context
id, outcome, and a `<select>` naming all three `DEMO_KNOB_IDS`) satisfies "pick which knob a delta
targets" directly and keeps the interactive surface small — one path for injection, not three
near-identical ones to keep in sync. Each of the three panels below it is a pure read of
`computeKnobView` for that knob; none of them carries their own, second copy of the injection UI.

## Decision 6 — revert is not "sticky" across further evidence, disclosed rather than silently assumed

`lib/arbitrate.arbitrate` is fully stateless: given the identical `priorState: live` and a fresh
`EvidenceTally`, it re-derives `revert` vs. `adopt` from that tally alone, with no memory of a PRIOR
call's own `revert` ruling. This file's own fold reflects that honestly: once a knob's phase reaches
`"live"`, every subsequently injected episode is added to a single, growing `monitoringEpisodes` pool
and re-evaluated against the WHOLE pool each time — so if a person injects enough further `"helped"`
episodes after a `revert` to flip `harmedMajority` back to false, the displayed decision will flip
back to `adopt`. This is not a bug this file introduces; it is what `arbitrate`'s own documented
contract produces when a caller (this UI) does not separately track "this delta was rolled back and
should never be reconsidered." Building that tracking was considered and left out: `lib/arbitrate`'s
own module comment already states plainly that tracking a knob's live/reverted history "is the
CALLER's job, not this function's," and inventing a persisted "permanently retired" flag this
milestone's own scope does not ask for would be exactly the kind of speculative flexibility this
account's own standing discipline warns against paying for in unplanned rounds. Recorded here as a
disclosed consequence, not silently hidden behind a UI that stops accepting input once `revert`
fires.

## Decision 7 — `docs/WALKTHROUGH.md` was written now, against `localhost:3000`, not the deployed URL

`.genesis/PLAN.md` §3 (M8)'s own falsifiable check requires "a WALKTHROUGH.md script, beat-by-beat,
verified against the deployed URL in the same session it's written." Two tensions with that literal
text, both resolved here rather than silently either skipped or worked around:

1. **`docs/WALKTHROUGH.md` is nominally `M9`'s own file** — plan §3 (M9)'s "Scope" list names it
   directly, and M8's own "Files it owns" bullet does not. This is a real plan-boundary gap: M8's OWN
   falsifiable check cannot be satisfied without producing a file M9 is also named as owning. This
   milestone resolves it by writing the file now, since M8's falsifiable check is concrete and
   present-tense ("verified... in the same session it's written") while M9 has not started — M9
   should treat this file as already delivered and revise it if a later milestone's own scope
   requires changes, not re-invent it from scratch.
2. **Deploying was explicitly out of scope for this round** (see this milestone's own PR/report): the
   Vercel CLI was logged out and `VERCEL_TOKEN` was not in the environment, with the token mid-
   rotation by the account holder. "Verified against the deployed URL" was substituted with
   "verified against a real, running `npm run dev` session on this machine" — every beat in
   `docs/WALKTHROUGH.md`'s own verification section was captured from an actual browser session
   against `localhost:3000` in this same session, not written from intentions and checked later. This
   substitution is stated plainly at the top of that file and is not silently narrowed into the
   original plan language.

**No forward promise is made about when the deployed URL will reflect this milestone** — only that it
currently does not, and that `docs/WALKTHROUGH.md` names this explicitly.

## Decision 8 — the frozen knob's panel is NOT special-cased: its episodes are passed to the real engine (a disclosed deviation from the plan's literal text)

`.genesis/PLAN.md` §3 (M8) says the protected knob's panel is "`frozen` from the first render, with no
code path that recomputes it from injected episodes at all." This milestone does not follow that
sentence literally, and did not say so until L4 VERIFY pointed it out. `computeKnobView` has no branch
on `knobId` (a reading of the source; no test pins the absence of a branch): for `auto-refund-ceiling`
it passes every injected episode to `evaluateDelta` exactly as for any other knob. The decision is
`frozen` because, in `arbitrate` (`lib/arbitrate/arbitrate.ts`, lines 244-262), after its `tally.deltaId`
consistency check, `gateResult === "frozen"` is ruled on before any of the tally's counts are read;
`evaluateDelta` itself computes the tally first (`scenario.ts`, lines 82-87).

**Why this is the better design for this artifact:** the claim the demo exists to make is that
`frozen` is immune to evidence that WOULD have adopted. A panel that ignored the episodes it was
handed, or printed a constant, would show a viewer "nothing happened" without showing that the engine
was ever given the evidence — it would demonstrate the UI's own special case, not the engine's
immunity. Passing the same kind of evidence that adopts `escalation-aggressiveness` to the real
functions and reading `frozen` back is the demonstration, and it keeps every rendered decision a real
engine return value. A hardcoded `frozen` for that panel would be exactly the "string describing what
the engine would do" this milestone refuses.

**What a test pins about this, and what it does not** (`compute-demo-view.engine-spy.test.ts`, added in
Round 3; both functions are wrapped with pass-through spies and still run for real). For
`auto-refund-ceiling` with 3, 500 and 10,000 distinct helped episodes: `evaluateDelta` is called with a
list that grows from 0 to N, ending in exactly those N episodes, in order, under the knob's own delta
id; `arbitrate` is handed an N-distinct / N-helped tally with `gateResult` `"frozen"` on every call and
returns `frozen` on every call. For the same three tickets given to both knobs, `arbitrate` receives
identical counts, differing only in `gateResult` (`eligible` vs `frozen`) and in the resulting decision
(`adopt` vs `frozen`). **Not observed:** `tally` and `gate` are not wrapped, so the hand-off from
`evaluateDelta` to them is established only by the tally `arbitrate` receives having the episodes'
counts. Before Round 3 the claim that the episodes "reached the engine" rested on assertions that pin
only that they are RETAINED in the pool the view hands to `evaluateDelta` — a mutant that kept the pool
but called `evaluateDelta(delta, [], ...)` passed all 380 tests.

**What is preserved:** the panel never shows `hold`, `adopt` or `revert` and is `frozen` from the first
render, in every history these tests drive — pinned by the zero-episode test, the 5-episode and
10,000-episode tests, the "never leaves trial" test (500 episodes), and the `KnobPanel` render test for
the protected knob after three helped episodes. The 10,000- and 500-episode tests also assert the
episodes are retained in the view's pool, which makes them fail against a view-model that drops them.

**What is weakened, stated plainly:** "no code path recomputes it" was a property of the source that a
reader could verify by inspection. "Frozen regardless of evidence" is now a property of the frozen
engine's behaviour — in `arbitrate`, after its `tally.deltaId` check, `gateResult === "frozen"` is
ruled on before any of the tally's counts are read (a reading of the source) — whose consequence (a
10,000-episode tally with `gateResult` `"frozen"` still yields `frozen`) is pinned by
`lib/arbitrate/__tests__/frozen-wins.test.ts` and exercised through the UI by the tests above, rather
than being a property of the UI's absence of a path. A regression in `arbitrate` that let evidence
influence a frozen delta would now show up in this panel's decision; that is the point, but it is a
different guarantee than the plan's sentence promised.

## Falsifiability — the gutting experiment, re-run on the final test suite

`computeKnobView`'s entire replay-fold body was temporarily replaced with a stub that ignores its own
`inputs` parameter (every knob permanently evaluated against zero episodes, forever `"trial"` phase),
kept typecheck-clean (`void inputs; void toEpisode; void liveOn;`) so the count below reflects semantic
sensitivity, not an unrelated build break. `npm test` was then run against the full suite, on the
suite as it stands after Round 3 (the first revision of this section, run against 360 tests, is
superseded; Round 2 explains why it was incomplete; the Round 2 revision, 380 tests, is superseded by
the four engine-spy tests added in Round 3, which fail under this sabotage and change no other count):

- **355 of 384 tests still pass; 29 fail**, all 29 inside `components/__tests__/`. The 342 tests that
  existed before this milestone are untouched by design (`lib/**` and `domains/**` are not edited).
  Of the 42 tests this milestone owns, **29 fail and 13 pass**.
- **All 13 passes are accounted for below — each is correctly insensitive to this specific sabotage,
  for a stated reason.** (The first revision of this section accounted for 8 of 9 passing tests; the
  ninth, `every decision's own tally.deltaId matches this knob's delta id, by construction`, had no
  stated reason because it had none: it checked one decision, and asserted a property `arbitrate`'s own
  throw already guarantees. It has been replaced; see Round 2, finding 4.)
  - `zero episodes -> TRIAL phase, hold, needs 3 more distinct contexts, empty tally` and `zero
    episodes -> frozen, citing this domain's own invariant id, with no evidence-shaped field at
    all` — the gutted function's own fixed output IS the correct zero-episode answer.
  - The three `every corpus string ... evaluates without throwing` tests (one per knob, under the
    describe `a fixed corpus of adversarial strings does not make the view-model throw`) — a function
    that ignores its input cannot throw on it. These pin "does not throw", not output correctness; the
    corpus test that pins output (`the 15 corpus strings ... adopts at the third`) fails.
  - `computeKnobView is pure` and `computeKnobView does not mutate the input history` — a function
    that ignores its input is still deterministic and cannot mutate what it never reads. Purity and
    non-mutation are different properties from correctness, and these tests claim only the former.
  - The two construction-invariant tests (three distinct delta ids; each delta's `knob` field matches
    its key) — assert facts about the `DEMO_DELTAS` constants, never about the replay logic.
  - In `AdaptiveAgentDemo.test.tsx`: the three static-render tests (initial render shows `HOLD` and
    `FROZEN`; the protected panel never shows `ADOPT`/`REVERT`; the spelling-drift note) pass because a
    static server render can only ever show the zero-episode state, which is exactly what the gutted
    function returns — a disclosed limit of that kind of test, which is why the panel and
    `describeDecision` tests above them drive real mid-story views; the note test is independent of the
    view-model entirely and is pinned against its own mutant (below). And `describeDecision frozen:
    cites this domain's own invariant id` passes because `frozen` is evidence-invariant, so the gutted
    function's frozen decision is identical to the real one; that test's sensitivity is to the
    formatter (mutant F), not to the fold.
- The 25 failures include, by name, every test that drives an episode history and expects the decision
  to move: the hold/adopt/revert story tests, the neutral cases, the replay-storm test, both
  spelling-drift tests, the 15-string corpus adoption test, the three per-knob recount sweeps, all five
  `describeDecision` tests that use a non-frozen decision, all four `KnobPanel` tests, the 5-episode,
  10,000-episode and 500-episode frozen tests (which also assert the episodes are retained in the view's
  pool), and all four engine-spy tests (a stub that never calls `evaluateDelta` with any episode
  cannot satisfy them).
- `components/compute-demo-view.ts` was then restored byte-for-byte (`git diff` on it empty
  afterwards), `npm run typecheck` and `npm test` re-run clean (380/380).

## Round 2 — L4 VERIFY findings, each fixed for real

L4 VERIFY rejected the first revision. Every gate passed, the frozen diff was empty, and engine-level
sabotages (`arbitrate` -> always-adopt, `gate` -> always-eligible, `tally` -> all-zero) all failed the
view-model tests as they should. The defects were in claims, and in which values the tests actually
pinned. Each was reproduced before it was fixed.

1. **"Exactly two throw conditions" contradicted its own cited proof.** The `grep` cited as evidence
   returns three `throw new Error` sites in `lib/arbitrate/arbitrate.ts`. Fixed in the view-model
   comment and Decision 3: three sites, two caller-inducible, one defence-in-depth guard; this UI
   reaches none; and the fourth throw site, `mustEvaluate`, is this milestone's own and is now
   disclosed. (The independent verifier's fuzz of 4,000 random `computeKnobView` calls, including
   `__proto__`, NUL, RTL overrides and a 1,000,000-character string, threw zero times; the suite now
   carries a fixed corpus of that shape as a regression pin, not a proof.)
2. **The bug fixed in Decision 2 was not pinned by the values it was about.** No test asserted
   `helped`, `neutral` or `harmed`. Mutant M-D (an `adopt` carrying `helped: 0` with `distinctContexts`
   intact) and mutant M-C (a `revert` carrying `distinctContexts: 0, harmed: 0`, which renders `REVERT
   to 0.5 — tally: 0 distinct ... harmed=0`) both passed 360/360. Every tally assertion now pins all
   four counts, including the adopt-on-last, revert-on-last and one-harmed-after-adopt tests. **M-D now
   fails 8 tests and M-C fails 6.** Re-adding the original post-loop bug (M-B) now fails 7, including
   the test named for the behaviour (`3 distinct helped episodes -> flips to LIVE, adopt ON THE LAST
   EPISODE ...`) — before, it was caught only by the spelling-drift test's `distinctContexts === 3`.
3. **The rendered text was not pinned at all.** Mutant M-F (`describeDecision` hardcoding `"HOLD —
   hardcoded"` and `"FROZEN — invariant: hardcoded"`, ignoring the engine) passed 360/360 — the
   defect class this milestone exists to avoid, resting on one manual browser pass. `describeDecision`
   and `KnobPanel` are now exported (nothing else imports them) and tested against REAL views from
   `computeKnobView`, with literal expected strings rather than the template under test. **M-F now
   fails 5 tests**, and so does M-F2 (the same, hardcoding `ADOPT`/`REVERT`).
4. **All passing tests in the gutting decomposition are now accounted for** (see Falsifiability above):
   the ninth, unexplained test was replaced by a sweep over all three knobs at every prefix of one fixed
   mixed 9-episode history, asserting that the episodes the VIEW RETAINS carry the knob's own delta id and
   are exactly the input history in order, and that the displayed tally equals an independent recount of
   the pool the decision came from.
   Decision 3's "construction invariants pin this" was narrowed: mutant M-E (a duplicate delta id)
   fails exactly one test of 380, the distinct-ids constants test, and the ADR now says that is all
   those tests pin.
5. **Undisclosed plan deviation** — the protected panel replays its episodes through the engine rather
   than having "no code path that recomputes it from injected episodes". Now Decision 8, with the
   reasoning and what it weakens.
6. **The spelling-drift note was unpinned.** Mutant M-G (note deleted) passed 360/360. The render-smoke
   test now asserts its text, all three example spellings and that it sits inside the form. M-G fails
   exactly that test.
7. **A dangling reference** to an ADR "traps" section that does not exist, in `compute-demo-view.ts`
   and in Decision 4, is fixed (the section was the build brief's vocabulary, not a repo artifact).
8. **The PR body** still said five commits and a "~75-second" walkthrough; refreshed.

**Further unpinned values this round found on its own**, by running the same kind of mutant against
values L4 VERIFY did not name — each passed 360/360 before and fails now: mutant M-N (an `adopt`/`hold`
carrying an inflated `neutral`; no test had ever asserted `neutral`) fails 17; mutant M-H (the panel
always printing the `TRIAL (pre-adoption)` phase label) fails 2; mutant M-I (the panel printing
hardcoded `0 trial episode(s), 0 monitoring episode(s)`) fails 4. And the "10,000 episodes still
frozen" and "never leaves trial" tests were vacuous against a view-model that DROPPED the episodes
(it would also report `frozen`); both now assert the episodes are retained in the view's pool. That
fix was worded more strongly than it pinned ("reached the engine"); Round 3 corrects the wording and
adds the test that observes it.

## Round 3 — L4 VERIFY's second rejection: wording, and one property no output could show

L4 VERIFY reported that the substantive fixes of Round 2 held: about twenty distinct mutants fail
against the suite, the rendered-text tests are not circular, the recount sweep is independent, and each
of the 13 tests that pass under the gut matches its stated reason. Its second rejection named a
pattern, and this round is written to it: **a sentence
written to repair the last defect claimed more than the test pinned** — three rounds running (the
throw-site count in Round 1, "reached the engine" in Round 2, and Decision 8's rationale resting on it).
Every sentence changed below is meant to be exactly as strong as a test that can be pointed to.

1. **"Reached the engine" was not pinned.** M-X1 (protected knob silently drops every episode) failed 5
   tests, so the Round 2 fix worked against dropping. M-X2 (the view KEEPS `trialEpisodes` but hands
   `evaluateDelta` `[]` for the protected knob) passed 380/380: a frozen decision carries no tally, so
   receipt is unobservable from the output, and the Round 2 tests pinned only that the episodes are
   retained in the pool the view hands over. `compute-demo-view.engine-spy.test.ts` now wraps
   `evaluateDelta` and `arbitrate` with pass-through spies and asserts what they are called with (see
   Decision 8 for exactly what is and is not observed). **M-X2 now fails 4 tests, all in the new file;
   M-X1 now fails 9.** Every site that said "reached the engine" or "handed to the engine" is reworded
   to the boundary that is actually observed: the episodes are passed to `evaluateDelta`, and
   `arbitrate` is handed a tally counting them. (Commit `4aae519`'s message still says "really
   reached the engine"; history is not rewritten, and this paragraph is the correction.)
2. **"Gate before tally" was wrong about the call chain.** `evaluateDelta` computes the tally first,
   then the gate verdict, then calls `arbitrate` (`scenario.ts`, lines 82-87). Inside `arbitrate`, the
   `tally.deltaId` consistency check runs first, then `gateResult === "frozen"`, before any of the
   tally's counts are read (lines 244-262). A `tally` refusal for the protected knob would therefore
   still throw in `mustEvaluate` before frozen is considered. Decision 8 and the view-model comment now
   say that, and mark it as a reading of the source whose behavioural consequence is pinned by
   `lib/arbitrate/__tests__/frozen-wins.test.ts`.
3. **Two small corrections.** The corpus `describe`, `no string a text field can produce makes the
   view-model throw` (a universal claim that appears as such in test output), is retitled `a fixed
   corpus of adversarial strings does not make the view-model throw`; the sweep describe no longer

## What this milestone does not claim

- **Not a claim that `arbitrate` can never throw for any caller** — only that this UI's own
  construction reaches none of its three throw sites (two caller-inducible, one defence-in-depth),
  nor the fourth in `mustEvaluate` (Decision 3).
- **Not a claim that the protected knob's panel has no code path that recomputes it from injected
  episodes** — it has one, by choice (Decision 8), and the plan's literal sentence is not followed.
- **Not a claim that `tally` and `gate` receive the protected knob's episodes as observed fact** —
  they are not wrapped; only `evaluateDelta`'s and `arbitrate`'s arguments are spied (Decision 8).
- **Not a claim that the form's click handling is tested** — mutant M-W passes (Round 3).
- **Not a claim that revert is permanent** — Decision 6 discloses the opposite: further evidence can,
  in principle, flip a reverted knob back to `adopt`, matching `arbitrate`'s own stateless contract.
- **Not a claim that the deployed URL reflects this milestone** — Decision 7 and this milestone's own
  PR/report both state plainly that it does not yet.
- **Not a claim about M9.** This ADR records that `docs/WALKTHROUGH.md` was written now because M8's
  own falsifiable check required it; it makes no promise about what M9 will or will not do with it,
  and no claim that any other M9-scoped document (README's "Limits" section, `docs/ARCHITECTURE.md`,
  `docs/THESIS.md`, `docs/NOTES.md`, the Loom recording itself) exists yet.
